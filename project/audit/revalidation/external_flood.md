# A. Research Direction Assessment

The proposal conflates several distinct tasks – unsupervised anomaly detection via reconstruction, current‐flood detection, future threshold‐exceedance prediction, numerical discharge forecasting, and operational alerts under real‐time constraints. These tasks have fundamentally different aims, labels, inputs and evaluation requirements. For example, **reconstruction‐based anomaly detection** attempts to flag unusual input patterns (high reconstruction error) without explicit flood labels. It typically uses a model trained on normal conditions only and issues an anomaly score (often based on reconstruction or latent metrics). Such methods can only *suggest* that something out-of-distribution is happening, but cannot explicitly predict a flood threshold crossing unless that anomaly score is proven to precede floods. In contrast, **event detection** (already-occurring flood) is a supervised classification problem: given inputs up to time *t* (e.g. recent streamflow, precipitation), decide if the river stage is currently above flood threshold. Labels come from stage exceedance at *t*. **Threshold prediction** is also a supervised task, but labels are future-oriented: given data up to issue time *t₀*, predict whether the stage will exceed a given threshold within some future window [*t₀+Δ1*, *t₀+Δ2*]. **Discharge forecasting** is regression: predict future streamflow/stage time series at specific horizons. **Operational warning** integrates forecasting with real-time data constraints: models must use only information actually available at each issuance time (e.g. no future precipitation). The label is typically the *onset time* of flood, which may be interval-censored (we only know it occurred between discrete measurements).

**Claims and labels:** A reconstruction method could only claim to detect anomalies or precursors, but *not* reliably “forecast” a future flood. By contrast, forecasting or threshold‐prediction models explicitly claim to predict future flows or exceedances and must be evaluated with held-out future targets and appropriate lag configurations. For anomaly detectors, valid labels would be rare events (flood days) and the hypothesis is that they correspond to high anomaly scores; but this is a tenuous hypothesis unless supported by hydrological rationale. We must therefore **challenge** any assumption that a purely unsupervised reconstruction model provides useful advance warnings: mechanisms are unclear and must be tested as falsifiable hypotheses. For example, one could hypothesize that an autoencoder trained on normal low-flow regimes will produce high error during rapid runoff events; this could be tested by checking if reconstruction error peaks before known floods (and comparing to random times).

**Research coherence:** Currently, the proposal mixes these tasks in one engine. It needs a clear focus. We should critique whether the engine’s design (causal autoencoding network with MAE masking) addresses a well-posed problem. Reconstruction anomalies might at best detect large deviations (e.g. sensor failure or extreme input) but without ground-truth linking to floods, any “warning” is speculative. A more coherent aim is to *explicitly predict* future flood events or discharge and study that as the primary task, using anomaly metrics only as a supplementary signal. The project claims improved metrics on held-out data, but we must be careful: the 31 engine tests and 276 self-tests are code checks, not hydrological skill evidence.

**Contribution assessment:** The proposed model largely reuses existing components (causal TCNs/attention, gated LSTMs, masked reconstruction, Mahalanobis scoring, etc.). Its novelty seems to be the particular combination and data-adaptive loss metrics, not a fundamentally new learning theory. Given this, we should not assume intrinsic novelty; the contribution must come from *rigorous evaluation* (possibly negative or inconclusive) and clarity on when such methods fail or succeed. Feasible contributions include: (a) a careful negative-result study showing that reconstruction-based alerts do not outperform simple baselines under realistic conditions; (b) a benchmark evaluation that explicitly accounts for data availability and forecast timing (to avoid the “future data leakage” present in many studies); (c) analysis of how much labeled event data is needed (label efficiency) to train and evaluate such models; (d) examination of spatial/temporal generalization (training on some basins and testing on others). A defensible primary study might focus on one clearly defined task (e.g. “predict 48-hour flood exceedance at a gage using only past observations and gridded inputs”) with honest baselines (e.g. climatology, NOAA NWM outputs) and a thorough treatment of evaluation protocols. Optional extensions could then test reconstruction anomalies on top of this.

**Key points:** 

- **Observation vs Model:** USGS NWIS provides *true* streamflow measurements (but with variable latency and occasional gaps). NOAA’s National Water Model (NWM/NWPS) provides *modeled* flow forecasts at many locations. We must clearly distinguish them: *NWM* is suitable as a benchmark forecast (but its inputs include precipitation forecasts), whereas *NWIS* (USGS) is the ground truth for evaluation (though actual real-time availability must be emulated for fairness).

- **Data conventions:** gridMET and SNODAS are gridded hydrometeorological inputs (gridMET daily T, P, etc; SNODAS daily SWE). They are publicly available (CC0) and cover essentially the whole US, but use specific time conventions (gridMET’s “day” is MST). Importantly, **gridMET updates daily but has a 1–3 day latency**, and SNODAS is a daily model product (not hourly), so they cannot capture within-day rain events directly.

- **Provenance and Latency:** We must **not** assume perfect retrospective knowledge. For a valid operational study, one should simulate the data feeds as they would have appeared *historically*. For example, use only gridMET data as it was available up to the forecast issue time (not with later revisions), and similarly for any reanalysis. Tools like PRISM or NLDAS would have been the original sources, so gridMET’s methodology (melding PRISM and reanalysis) suggests ~1-2 day latency for the latest data. SNODAS is run daily at 00Z, so it should be available within a day of “real time”.

- **Flood-stage thresholds:** Official flood categories (action, minor, moderate, major) are defined for each gage, but these change if the gage datum or channel is re-surveyed. Historical flood warnings from AHPS/NWPS might not be easily obtainable for past dates. For labeling events, we may instead define floods via exceedance of a fixed percentile (e.g. 90th percentile daily flow) or use documented peak events in datasets like NCEI Storm Events. Citing NOAA/NWS, NWPS uses stage categories updated as of March 2024, but we cannot retroactively access historical threshold changes. This uncertainty suggests focusing on relative flood metrics (exceedance of historical flows) rather than absolute stage.

- **Authentic inputs:** We should require **realistic availability flags**. For example, forecasts at 0 UTC should use observed USGS flows up to ~23:45 prior day (not the future), forcing through gridMET up to day-1, SNODAS up to day-1, and no knowledge of future precipitation beyond climatology or ensemble forecasts. If a needed source (e.g. NLDAS) isn’t feasible, we could use gridMET as a proxy, but must note any differences. If any source truly cannot be replicated (e.g. operational radar QPE beyond NOAA archives), we should narrow the scope (e.g. restrict to daily lead forecasts using only reanalysis and rain gauge data).

- **Minimal input set:** At minimum, an honest study requires (a) recent historical precip/temperature (gridMET or similar), (b) snowpack or antecedent moisture (SNODAS or SNOW-17 outputs), (c) river flow/water level up to prediction time (USGS NWIS), (d) basin static attributes (if using a regional model; available from CAMELS/GAGES-II). If basin attributes are used, they must be static “known” features (area, mean slope, etc.), not future-derived. Any operational analog (like satellite rainfall nowcasting) should have realistic latency.

If any major data component is unavailable or unrecoverable in a timely manner, **do not replace it** with future data. For instance, if real-time SNODAS archives are not accessible, one might omit it and explicitly limit claims to no-snow scenarios or use a simpler snow index. The aim is an *honest study*, not a synthetic best-case.

# E. Study Design and Claims

**Population:** A well-defined study population is essential. For example, “All USGS stream gauges in the contiguous US with watershed area >10 km² and at least 20 years of continuous record (1980–2020) under mostly natural flow conditions.” If using CAMELS, that yields 671 basins. Within each basin, treat each *storm or flood event* as the unit of interest for detection/forecasting. We should explicitly group data into *independent events*: e.g., define floods by a peak and an antecedent dry period, ensuring events do not overlap.

**Splits:** Use a **spatial split** (train on some basins, test on others) if evaluating regional generalization, or a **temporal split** (train on earlier years, test on later years) to simulate future forecasting. Best is a combination: e.g. train on many basins through 2010, validate on others or later. Always enforce a *warm-up* period on test basins (e.g. first X days to initialize state). Use **purge/embargo rules** to avoid temporal leakage: if sliding windows overlap, ensure that events in train don’t leak into test windows within the same event period.

**Event labeling:** Define an *onset time* for each flood event as when stage exceeds action or minor threshold, or a discharge exceeds some high percentile. If only daily data, onset is interval-censored (some time during day). We can treat it as “flood on that day”. The target could be “first flood day after train cutoff”. For forecast evaluation, we could use an hourly target if high-frequency data are available, else daily peak.

**Missed/ongoing floods:** If a flood is already underway at a forecast issuance, mark that as continuing-flood; alerts should only be evaluated on new onsets. E.g., only score a hit if a flood starts in the future window, and ignore alerts issued during an ongoing flood (this defines a proper positive/negative window).

**Alert matching:** We should set a clear **alert protocol**. For each issuance time, the model outputs a score or probability of a flood onset within the next *H* hours. We convert to binary alerts by a threshold (to be set on a development set). Evaluate using standard event-based metrics: *hit rate* (POD), *false alarm ratio*, *time-to-event* for correct alerts, etc. If multiple alerts are raised, only the first before the event counts (to avoid double-counting one event). If an alert is raised when no event occurs within *H*, it’s a false alarm. If no alert and no event, it’s a correct rejection.

**Continuous metrics:** Also evaluate **ranking metrics** (ROC/AUC, Precision-Recall) treating each issuance+window as one sample, scored by predicted probability or anomaly score. Use *paired tests* (e.g. DeLong’s test) to compare AUCs if doing significance.

**Calibration:** Use the training set to calibrate any probability outputs (e.g. Platt scaling or isotonic regression) and to pick a decision threshold that meets an operational criterion (e.g. maximum 1% daily false-alarm rate). Thresholds or calibration must not see test data.

**Statistical analysis:** Since basins and events vary, use a hierarchical testing approach. For example, compute per-basin performance metrics on test basins, then average. Use *paired comparisons* (e.g. paired by basin or by event) to test differences. Control for multiple comparisons if many metrics. Report confidence intervals (e.g. via bootstrapping basins or events).

**Success criteria:** The study should clearly define what would constitute (a) benefit (significantly higher hit rate for same false-alarm rate, or significantly better AUC), (b) degradation (worse metrics than a simple baseline, e.g. persistence or climatology), (c) equivalence (statistically indistinguishable performance), or (d) infeasibility (e.g. method fails to train or passes no events). Any poor result with an *invalid protocol* (e.g. leaked data) is *not* a valid negative conclusion.

Concretely, if a reconstruction-anomaly method cannot beat a null predictor (such as “alert if yesterday’s flow was high”), it should be reported as a true negative result, not whitewashed. But to be credible, all aspects (split, labeling, skill metric) must be rigorously defined as above.

# F. Pilot Performance and Compute Plan

Given the Apple M3 Air hardware (8-core CPU, 10-core Apple GPU via MPS, 16 GB unified memory), we should conduct small-scale benchmarks **before the full study**. For example:

- **Numerical correctness:** Run a simple TCN or LSTM on dummy data (e.g. sine waves) to verify the model runs under MPS, produces consistent results across runs (spot-check determinism), and to measure throughput. Compare single-thread CPU vs MPS GPU speeds for a moderate batch (e.g. batch=16, sequence=30, hidden=64).  
- **Memory tolerance:** Gradually increase model size (stack depth, hidden dims) and batch size until memory (16 GB) is near full. Record the maximum batch/hidden we can handle without running out. Also test the data pipeline (can the dataset loader stream preprocessed data without copying too much?).  
- **Streaming vs batch:** If the factory code or data pipeline does sliding windows, ensure it doesn’t materialize all windows at once. Plan for using lazy or chunked loading.  
- **Attention memory:** Attention layers scale O(seq²) memory. If seq length=30 is OK, what about 100? Likely we must keep windows short (≤50) or avoid full attention.  
- **Optimizer state:** Check that MPS supports chosen optimizers (e.g. Adam). Some PyTorch ops may be CPU-only on MPS; fallbacks are slower.  
- **Batch vs update:** Smaller MPS batches may reduce GPU utilization, so test how batch size affects training speed.  
- **Random seeds:** Note that complete bitwise reproducibility may be difficult on Apple GPU; quantify run-to-run variance (train the same model twice and measure output stats).

We **must measure**, not assume: for example, create a stopwatch test of training an epoch on 1000 samples. Also measure end-to-end data loader time vs computation.

If full-scale training (e.g. hundreds of basins, many epochs) exceeds what the M3 can do in a reasonable time (days), propose reductions: e.g. train on 50 basins instead of 500, or reduce hidden dimensions. But we should justify any reduction scientifically: it should not drop to where model has no capacity. Perhaps focus on a subset of basins with strong flood history. Any hardware-driven trade-off should be explicitly described (e.g. “limited to 64 hidden units due to memory; might affect modeling of complex patterns”).

Finally, plan for result averaging: e.g. only 3 random seeds rather than 8 or 10, if training one seed is already hours long. Note that MPS can be slower per operation than high-end GPUs, so be conservative.

# G. Factory Integration Assessment

The Factory v3.3 framework is a general-purpose ML execution system. We should verify which research requirements it **enforces** and which it merely **declares**:

- **Enforces:** It likely enforces that code runs with a fixed seed, records outputs, and stores a provenance (Git hash). It might check that configuration (including dataset paths) is logged, and it may automatically save model weights and metrics. These help reproducibility. We should ensure that the commit SHA (4e9e4be…) is indeed captured in the results metadata.

- **Declares:** It may assume the domain specification is correct, but it cannot itself ensure the labeling or evaluation logic is sound for floods. For example, it might declare a “test set” but not verify that test examples are truly held out events. Also, it may generate figures or stats on *whatever* predictions come out; it cannot know if an anomaly score is being misinterpreted as a flood probability.

- **Cannot establish:** The framework cannot enforce that the model only uses allowed data (e.g. it won’t know if hidden future inputs leaked). It also cannot guarantee scientific validity: passing a “factory gate” (all code tests, metrics computed) is not evidence of hydrological skill. We must not rely on its built-in metrics (e.g. mean-squared error on train/test) as final word on validity. The domain adapter we provide must implement correct metrics (e.g. event-based skill).

We should audit:
- **Dependency loading:** Does the factory isolate the Python environment (e.g. using `venv` or container)? If not, variations in library versions can affect results. We should record exact library versions (PyTorch, numpy, etc). 
- **Interpreter identity:** It may run `python` but on an M3 that could be either ARM Python or x86? We need to confirm we are using ARM binaries (M3 has ARM architecture). Mismatches could affect reproducibility (especially with MPS backend).
- **Execution args:** Check that command-line args (like number of threads) are fixed. For example, ensure MPS is set (sometimes one must set environment `PYTORCH_ENABLE_MPS_FALLBACK=1` or similar).

# H. Audit & Implementation Agenda

We should plan a staged audit of the code and method, with acceptance criteria for each item:

1. **Data adapter readiness:** Confirm we can ingest USGS flow data, gridMET, SNODAS etc. into the framework. *Acceptance:* Successfully load a sample basin’s data (e.g., Colorado River at Lees Ferry) and verify values against known sources (e.g. NWIS website).
2. **Causal layers test:** Verify all conv/attention layers are causal. *Acceptance:* On a contrived input (increasing sequence), ensure the output at final time matches a conv only over past values.
3. **Masking logic test:** For masked reconstruction, create a dummy 2-channel series, zero out one channel in input, train a trivial AE, and ensure the model’s output on the zeroed channel changes (i.e. it actually tries to reconstruct). *Acceptance:* Reconstruction loss decreases on that channel, proving target is absent in input.
4. **Loss masking test:** Introduce NaNs into input windows; ensure loss ignores them (e.g. a loss function returns zero error when both pred and true are NaN, or skip). *Acceptance:* Confirm via computing loss vector that masked entries contribute nothing.
5. **Forecast claim check:** Search code for any future target head; if none, adjust claim to “anomaly detection” only or add a forecasting loss (if aligning with research goal). *Acceptance:* Code either has a forecast output or documentation explicitly says no forecast is produced.
6. **Normalization correctness:** Compute means/std on training data, then on test data, and check code uses only first for normalizing test. *Acceptance:* Manual calculation matches code normalization.
7. **Window independence:** If using overlapping windows, check that training samples are drawn disjointly (or if repeated, that weights correct for it). *Acceptance:* Explain and demonstrate how many distinct events are effectively used for training vs how many windows; ensure no test sample ever overlaps a train window.
8. **Covariance sanity:** After training (or on random weights), compute the covariance matrix of latent embedding on train; check condition number. *Acceptance:* If ill-conditioned (>1e6), introduce shrinkage (e.g. add ε*I).
9. **Score interpretation:** For each anomaly score (recon error, latent Mahalanobis, latent-change), apply to a known flood event sequence vs normal. *Acceptance:* Provide a brief analysis (plot or stat) showing expected higher values on event period for at least one metric.
10. **Reproducibility trial:** Run the pipeline twice with same seed. *Acceptance:* Metrics (like AUC) must match within negligible tolerance (seed fixes initial weights and data shuffle).
11. **Dependencies logging:** Record exact versions of all libraries and the Git commit. *Acceptance:* Include a requirements.txt or environment.yml and code hash in the run outputs.
